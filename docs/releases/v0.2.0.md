# Tripwire v0.2.0

This release brings the redesigned dashboard and TypeScript workflow authoring to production. It also adds repository star checks for GitHub and ships the GitCafe integration behind its existing rollout controls.

## Workflow authoring

- Use the public TypeScript SDK to define workflows, then use the CLI to pull and push one file per workflow in `.tripwire/workflows`. Pushes retain the authored source for review and pull can return it verbatim. [Source round trip](https://github.com/Boring-Software-Inc/v2/commit/d4189cfb)
- Pull workflows built in the editor as SDK source, including graphs with branches and human review. Regenerate older exports when you want the current SDK syntax. [Graph export](https://github.com/Boring-Software-Inc/v2/commit/ed6c18c9) · [Regeneration](https://github.com/Boring-Software-Inc/v2/commit/175e9db0)
- Review pushes with a collapsible source diff, open the review from the CLI, and see clearer messages for duplicate names and new workflows. [Review diffs](https://github.com/Boring-Software-Inc/v2/commit/f3f62d81) · [Review links](https://github.com/Boring-Software-Inc/v2/commit/2fdfa77f) · [Push diagnostics](https://github.com/Boring-Software-Inc/v2/commit/c35e5f38)
- Require a contributor to own public GitHub repositories above a star threshold, or count merged pull requests in public repositories above that threshold. The second check can exclude repositories the author owns. [Repository star checks](https://github.com/Boring-Software-Inc/v2/commit/57eb7069)
- The CLI checks the project SDK before writing star-check workflows. Use SDK `0.1.4` or later with the stable CLI. The staging CLI has its own `tripwire-staging` command and tests against the staging SDK. [SDK compatibility](https://github.com/Boring-Software-Inc/v2/commit/311a7cf8) · [Staging executable](https://github.com/Boring-Software-Inc/v2/commit/b4085500) · [Channel verification](https://github.com/Boring-Software-Inc/v2/commit/316b8c74)

## Dashboard and moderation

- Updated the dashboard shell, navigation, workflow editor, push review, run details, rules, responses, organization settings, sign-in, and agent authorization. The shell adapts between the desktop sidebar and compact header. [Dashboard redesign](https://github.com/Boring-Software-Inc/v2/commit/3a3c422f) · [Responses and settings](https://github.com/Boring-Software-Inc/v2/commit/2ecf9787)
- The moderation queue focuses on the active review, and a rerun shows its previous attempts together. [Moderation layout](https://github.com/Boring-Software-Inc/v2/commit/7a871a31) · [Run history](https://github.com/Boring-Software-Inc/v2/commit/1092ec6d)
- Rule properties open when the rule is the only member of its workflow group. Dashboard flag overrides follow the signed-in account. [Rule properties](https://github.com/Boring-Software-Inc/v2/commit/9d6484e4) · [Account-scoped flags](https://github.com/Boring-Software-Inc/v2/pull/162)

## GitCafe rollout

- Organizations can connect eligible GitCafe repos through verified account grants and explicitly enable native protection when the rollout is configured. GitHub mirror connections and native GitCafe protection are treated as separate paths. [Connection consent](https://github.com/Boring-Software-Inc/v2/pull/132) · [Forge repository controls](https://github.com/Boring-Software-Inc/v2/pull/141) · [Mirror and native behavior](https://github.com/Boring-Software-Inc/v2/pull/156) · [Protection activation](https://github.com/Boring-Software-Inc/v2/pull/160)
- Native workflows support verified pull request and comment events, push refs, scheduled work, and check reruns. Reviewer selection uses stable account IDs. Recovery paths retain in-flight decisions across delivery and head changes. [Pull request events](https://github.com/Boring-Software-Inc/v2/pull/144) · [Comments](https://github.com/Boring-Software-Inc/v2/pull/149) · [Push](https://github.com/Boring-Software-Inc/v2/pull/154) · [Schedules](https://github.com/Boring-Software-Inc/v2/pull/152) · [Reruns](https://github.com/Boring-Software-Inc/v2/pull/150) · [Reviewers](https://github.com/Boring-Software-Inc/v2/pull/155) · [Recovery](https://github.com/Boring-Software-Inc/v2/pull/158)

## Staging pilot

The shared spam blocklist is available only to the configured staging repo. A maintainer with the rollout flag can opt in from **New in Tripwire** or manage the review-only rule in **Rules**. A match on a current snapshot sends the pull request to Human review. The public directory and read-only JSON API use the same GitHub snapshot, which starts empty. [Pilot scope and rollout](https://github.com/Boring-Software-Inc/v2/issues/189) · [Snapshot repository](https://github.com/Boring-Software-Inc/tripwire-shared-blocklist)

## Upgrade and release checks

- Publish the stable SDK first, then verify the stable CLI package against it. Existing local installations update when the maintainer installs the new packages. [Stable SDK promotion](https://github.com/Boring-Software-Inc/tripwire-sdk-typescript/pull/1)
- Verify database migrations `0045` through `0049` for forge delivery isolation, GitCafe account bindings and lifecycle, installation accounts, and event completion. [Migration diff](https://github.com/Boring-Software-Inc/v2/pull/190/files)
- Verify the production deployment points to the merged promotion commit, run a real production smoke check, and dispatch **Publish product release** from `main` with the promotion PR and public smoke run ID.
