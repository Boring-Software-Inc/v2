# GitCafe receipt admission and installation retirement

This staging slice starts from `a50a5cea751600ed8a5d31565ace1c0a07e2c0cd`. It adds raw receipt admission and an isolated lifecycle consumer. GitCafe normalization, workflows, and forge actions remain unavailable. No environment setting, app setting, deployment, or live installation was changed during implementation.

`POST /webhooks/gitcafe` remains disabled by default. Configuration requires `GITCAFE_WEBHOOK_RECEIPTS_ENABLED=true`, `UNKEY_ENVIRONMENT_SLUG=preview`, the dedicated staging `GITCAFE_APP_ID`, and `GITCAFE_WEBHOOK_KEY_VERSION` / `GITCAFE_WEBHOOK_SECRET`. These are rollout inputs for the parent; this work does not enable them. Receipt admission verifies HMAC over the Unix timestamp, a dot, and the exact bytes, with a five-minute age limit and 30-second future allowance. Both declared and streamed bodies are bounded to 1 MiB. The event header must match the body's type. Signatures and secrets never enter receipt rows or jobs.

`gitcafe_receipts` retains the exact bytes as base64 plus a SHA-256 digest, parsed envelope, delivery ID, signing timestamp/key version, and request ID. `(installation_id, event_id)` is the semantic dedupe key. Receipt insertion and `gitcafe-lifecycle` enqueue share one PostgreSQL transaction. Receipt bytes and metadata are immutable; only processing status and time change. Unknown event types park without normal ingestion or effects. Invalid lifecycle shapes become `malformed` without changing installation or repository state.

The consumer handles `installation.created`, `installation.repositories_updated`, `installation.paused`, and `installation.uninstalled`. These are the provider's actual names. GitCafe app suspension emits no webhook. Created events never claim an organization, create repos, restore visibility, or arm anything. Actor IDs and provider organization names/IDs are not ownership evidence. A verified uninstall is terminal for that installation ID. Reinstallation uses a new ID.

Repository removals disarm and soft-remove only rows matching `forge = 'gitcafe'` and the exact installation ID. Complete selected-to-selected updates can retire the removed repository IDs. Transitions involving all repositories or truncated removal lists withdraw visibility for the installation until fresh reconciliation. No installation/repository count cap is introduced. Existing repository rows, claims, runs, and audit history remain. No lifecycle path restores visibility or arms repos.

`gitCafeLifecycleServices` exposes these parent integration points:

- `retireGitCafeInstallation(db, { installationId, reason })`: withdraws that installation's visibility and arming. Reasons are `reconcile-required`, `paused`, or `uninstalled`. Use terminal uninstall only with authenticated lifecycle/provider evidence.
- `reconcileGitCafeInstallation(db, { installationId, expectedAppId, expectedOwner?, organizationId?, lookup })`: the injected callback performs a fresh lookup using the existing installation client. When supplied, the owner and Tripwire organization restrict cleanup to their existing claim. A failed, malformed, thrown, or mismatched provider lookup withdraws requested authority as `reconcile-required`; a generic 403 is not classified as uninstall. A matching fresh installation response may remove stale selections but never adds visible repos. Regressing provider version/revision cannot replace newer authority, and terminal uninstall cannot be reversed.
- `getGitCafeActionAuthority(db, installationId, generation?)`: denies absent/inactive authority and pending revocation receipts. Future action callers must check before minting and immediately before using credentials, carrying the returned generation and invalidating cached credentials when it changes. Existing person/session/org and per-repository authorization remains required.
- `insertGitCafeReceipt(pool, boss, receipt)` and `processGitCafeReceipt(db, receiptId)`: internal admission and consumer handoff; these services do not verify an HTTP signature themselves.

Retirement and reconciliation share the existing connection writer's `gitcafe-connection` advisory lock. A local generation rejects a lookup that spans a concurrent lifecycle change. Provider versions/revisions cannot move backwards. A fresh lookup's start time supersedes older non-terminal events. Without newer fresh authority, delayed removal/pause events can still withdraw access; a later event cannot grant it back. Receipt replay returns the recorded status without repeating writes. Uninstall remains terminal regardless of delivery order.

With `GITCAFE_WEBHOOK_RECEIPTS_ENABLED=true`, the existing isolated `gitcafe-connect` worker consumes both GitCafe queues. Before a connection it reconciles the current installation and prior claims belonging to the same Tripwire organization and forge owner. Reclaiming a stable repository from a withdrawn installation preserves its row and history; other tenants and active unrelated claims remain protected. Ownership writes recheck lifecycle generation and pending revocations under the shared lock.

The separate `WORKER_MODE=gitcafe-lifecycle` also requires the receipt flag, preview environment, and dedicated staging app ID. It registers only the lifecycle queue and requires no forge signing key. Both modes start no general worker consumers, schedulers, global maintenance, or deployment fence. Lifecycle recovery supervises only `gitcafe-lifecycle` at startup and every 30 seconds. Pending receipts whose jobs exhausted retries or were removed by retention receive new work atomically, in batches of 100, while queued or active work is preserved. The shared lock prevents concurrent recovery from duplicating jobs. Health names the registered queues and degrades on queue or recovery failure. The API also uses a producer without scheduler/maintenance when receipt admission is configured.

Migration `0047_gitcafe_lifecycle.sql` adds only the receipt and lifecycle tables and indexes. It does not change the old global event delivery index or migration `0045`. **Do not run the full pending migration chain on staging while the parent's `0045` rollout gate remains closed.** The parent must coordinate applying this additive SQL independently or sequence compatible ingestion before `0045`, using its normal migration ledger procedure. The isolated queue client requires the existing pg-boss schema and never migrates it.

The genuine `installation.created`, `installation.repositories_updated` (all-to-selected), and `installation.uninstalled` fixtures follow capture-fixture and independent validate-fixture audits: retained original response/payload hashes, metadata, owner-only permissions, recursive JSON equality, and privacy checks pass. Local receiver tests sign those bytes with a test-only key. Adversarial mutations test isolation, rejection, and parking; they are not additional provider captures. Fresh lookup tests reuse the existing captured installation and authored database state. A real pg-boss consumer test verifies completion while leaving general backlog and schedules untouched.

Remaining rollout evidence: a genuine `paused` delivery and live timestamped-HMAC receipt. The publisher UI exposed the real historical selection and uninstall deliveries after earlier delivery-list API reads returned 500. Downloading those payloads proves their recorded events and shapes, not their successful receipt or signatures at Tripwire. The parent owns deployment, scratch-only lifecycle testing, and the future action guard integration.

Protocol sources: [GitCafe webhook guide](https://git.cafe/docs/integrations/webhooks.md), [GitCafe OpenAPI](https://git.cafe/api/openapi/json). Both were read for this implementation; provider delivery evidence remains distinct from documented shapes.
